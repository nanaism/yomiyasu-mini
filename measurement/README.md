# 測定の記録

本体 yomiyasu v2.5.0 と yomiyasu-mini 1.2.0 に同じ原稿を推敲させ、書き直した文を本体 v2.5.0 の検査で数えました。1本ごとの数は [results.json](./results.json) にあります。本体 v2.4.0 から作った mini 1.1.0 の測定は [v2.4.0/README.md](./v2.4.0/README.md) に、本体 v2.2.2 から作った mini 1.0.0 の測定は [v2.2.2/README.md](./v2.2.2/README.md) にあります。

## 測り方

- 原稿: 本体 v2.5.0 の `tests/corpus/` から、`raw_ai/` の26本、`blacklist_ai/` の24本、`edge_cases/` の1本（`edge_kiku_45`）。mini 1.1.0 の測定と同じ51本で、どれも3回ずつ推敲させました。51本は本体 v2.4.0 の同じ名前のファイルと1バイトも違いません。
- 推敲させたもの: Claude Code 2.1.310 の claude-opus-5-5 で、effort は high です（`claude --print --model claude-opus-5-5 --effort high`）。本体と mini で同じモデルと設定を使いました。`--setting-sources project` を付けて利用者の設定を読ませず、CLAUDE.md と AGENTS.md を `claudeMdExcludes` で外し、MCP のサーバーも外しました。使える道具は Bash、Read、Write、Edit、Skill です（Agent、WebFetch、WebSearch は外しています）。
- 頼み方: 推敲の1回ごとに空の作業フォルダを作り、原稿を `draft.md` として置き、スキルを `.claude/skills/` の下に写しました。そのうえで「draft.md を yomiyasu で読みやすくして、結果を out.md に書いてください。」と頼みました（mini は「yomiyasu-mini で」）。使われたスキルが測るスキルだけであることを、1回ごとに Claude Code の記録で確かめています。
- 数え方: 原文と最終稿を本体 v2.5.0 の `yomiyasu_diff.py 原文 最終稿 --fail-on meaning-risk --json` に渡しました（`--doc-type` と `--stance` は渡していません）。「数える恐れ」は、`--fail-on meaning-risk` が数える意味が変わる恐れです。残った候補は `yomiyasu_lint.py 最終稿 --json` の warn 以上で数えました。書き換えた量は `difflib.SequenceMatcher(autojunk=False)` で一致しない区間ごとに原文と最終稿の長いほうの字数を足し、原文の空白を除いた字数1,000字あたりにした値です。入力トークンは Claude Code の記録の usage にある input_tokens、cache_creation_input_tokens、cache_read_input_tokens の合計です。

## 恐れを1件ずつ読んだ結果

本体の3件は `blacklist_ai/07_code_review_sonnet_casual` で2つ目の提案の文末「…見えないようにします。」を「…見えないようにしてください。」にしたもの（1回目と2回目）と、`raw_ai/04_slack_announce_sonnet_default` で「お願いしたいことは3点あります。」を「次の3点をお願いします。」にしたもの（1回目）です。どれも diff は文の種類が変わった恐れとして数えています。

mini の2件は、どちらも同じ原稿で同じ種類の恐れが本体の3回のどれにも出ていない、mini にだけ出た恐れです。

1. 1回目、`blacklist_ai/07_code_review_sonnet_formal`、文の種類の印（sentence_type / marks）
   - 元: また、外部APIの仕様変更やスキーマ変更が、業務ロジックの修正を伴う点も保守上の課題です。
   - 後: また、外部APIの仕様やスキーマを変更すると業務ロジックも修正が必要になる点も、保守上の課題です。
   - 読み: 名詞の主語「仕様変更やスキーマ変更が」を「仕様やスキーマを変更すると」の条件の節にし、「修正を伴う」を「修正が必要になる」にした。diff は必要の言い方が足されたとして数えた。変更があれば修正も要るという関係は同じだが、事実を述べる「伴う」が、必要を述べる「必要になる」に変わっている。SKILL.md の言い切りの強さの決まりで避ける書き換えに近い。
2. 2回目、`blacklist_ai/07_code_review_sonnet_casual`、消えた数値（number / lost）
   - 元: `OrderService.checkout` の中で、在庫テーブルへの直接クエリ、決済APIのHTTP呼び出し、割引計算のロジックが1メソッドに並んでいます。
   - 後: `OrderService.checkout` の中で、在庫テーブルへの直接クエリ、決済APIのHTTP呼び出し、割引計算のロジックが1つのメソッドに並んでいます。
   - 読み: 「1メソッド」を「1つのメソッド」にしたので、diff が「消えた数値」として数えた。3つの処理が1つのメソッドに並んでいるという意味は同じ。

mini 1.1.0 の測定では、mini は3回とも `blacklist_ai/07_code_review_sonnet_casual` の2つ目の提案の文末を依頼の形にしていました。この測定では、mini は3回とも「…見えないようにします。」のまま残しています。

ほかに数える恐れはありませんでした。

## 入れた決まりと外したもの

意味を守る決まりは SKILL.md の本文に置き、測定で外さない部品にしています。

意味の保持（最優先ルール）、情報が足りないときの暫定文、専門用語と名称の扱い、言い直しテストは、本体の文をそのまま写しました。置き換えたのは、mini にない道具やファイルを指す句だけです。情報を足さないことは、本体の節の最初の2段落をそのまま写し、AIへの指示が本文に残った文の段落を短く書き直しました（全文は `references/rules.md`）。言い切りの強さを上げないことは本体の「文書の立場と文末」から、条件・否定・因果・時系列を保つことは「段落と文の論理構造（つながり）」から、短く書き直して入れました。細部は参照ファイルに写しています。

本体 v2.5.0 で足された決まりは、次のように入れました。

- コードやシステムを説明する文書の擬人化（コードや資料から動作が分かるときだけ書き直し、分からなければ残して尋ねる）、否定で終わる定義文（何であるかを先に書く）、漢語の名詞で動作を省いた文（資料から動作が分かるときだけ動作の文にする）、依頼で指定された見出しの形とまとめを保つこと、推敲で新しく置く読点を残す読点の所だけにすることは、SKILL.md にそれぞれ短い文で入れ、本体の段落の全文を `references/rules.md` に写しました。
- Step 4 の目で見る点検に、原文より増えた読点が残す読点に当たるかを足しました。
- 本文に測定値を詰め込んだ文を表か箇条書きに分けるかを確かめる決まりは、`references/doc-types.md` の技術記事の分野の節に写しました。

本体 v2.5.0 で足されたもののうち、lint の変更（AI の文章によく出る言い回しの規則、直訳語の型1と型3、比喩の「効く」、短い目的語の「を、」の読点）と、lint が候補に出す言い回しの扱いを並べた slop-catalog.md の10章は、mini に lint がないので入れていません。diff と check の、見出しの形が変わった所と読点が増えた推敲を示す節も入れていません。検査のスクリプトの4本が上限の近くまで詰まっていて、入れるとスクリプトがもう1本要り、配るファイルが8つを超えるためです。本体の検査のスクリプトの呼び出し方の決まりと SKILL.md の `allowed-tools` も、mini はスクリプトの名前と呼び方が本体と違うので入れていません。audience.md の11章（読者像）に足された初心者向けの口調の項目は、参照ファイルの上限（100KB）に入らないので写していません。参照ファイルを上限に収めるために、SKILL.md や rules.md のほかの節と同じ中身の段落と行、言い直しテストの否定対比の節にある mini_check が出す形と出さない形の細部、同じ型の例が残る表の行を外しました。外した行と理由は [extract/table.json](../extract/table.json) の各部品の `note` にあります。

ほかに外しているのは、おもに mini にない道具に関わる手順と出力の欄です。lint の規則の名前、diff の文体の硬化と勢いの検査、diff の「原文にない人や担当を足した文」の候補、check の実行の記録（run と verify）、資料から事実を補う手順と「事実の確かめ」の欄、lint が読む語のファイル（`references/lists/`）、Step 5「提出の前の照合」がこれに当たります。部品ごとの扱いと理由は [extract/NOTES-content.md](../extract/NOTES-content.md) の8章と、[extract/table.json](../extract/table.json) の各部品の `note` にあります。
