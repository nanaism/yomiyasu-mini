# 文書の種類と分野、読者、書き手と読み手

SKILL.md「Step 1: 文脈と段落の把握」から指している細部です。本体 yomiyasu の、文書の種類ごと、分野ごと、読者、書き手と読み手の参照ファイルの節を、見出しを1段下げて写しています。

本文の節は、SKILL.md「最優先ルール: 意味の保持」のように、ファイルの名前のあとのかぎかっこで、yomiyasu-mini の本文の節の名前を書いて指します。`references/rules.md` の「本文の節の細部」に同じ名前の節があれば、そこも読みます。ファイルの名前を付けずにかぎかっこで示した名前（「業務・仕様・実務ドキュメント向け仕様」「書き手と読み手（ペルソナ）」など）は、この文書の見出しです。節の中の「1章」「4章の例」のような番号は、その節の中の章を指します。

## 種類の一覧

種類ごとに、当てない規則とその範囲です。種類を決めたら、この一覧と、その種類の節を読みます。

   | 種類 | 当てない規則（範囲） |
   |---|---|
   | pr（PR説明） | 箇条書きを地の文に戻す直し（変更点、確認したこと） |
   | article（技術記事） | なし |
   | incident（障害報告） | 箇条書きを地の文に戻す直し（時系列）、硬い漢語の言い換え（発生、復旧などの報告の語） |
   | proposal（提案書） | なし |
   | minutes（議事録） | 箇条書きを地の文に戻す直し（太字のラベルを含む） |
   | manual（マニュアル） | 箇条書きを地の文に戻す直し（番号つきの手順） |
   | slides（スライド） | 箇条書きを地の文に戻す直し（太字のラベルを含む）、数の宣言と繰り返すだけの「まとめ」の整理、体言止めの項目での主語の抜けと文末の直し、箇条の「〜のは、A、B、C」の直し |
   | essay（エッセイ・小説） | 読み取れる比喩の言い換え（エッセイの比喩動詞は直す）、小説の本文のコピー調とダッシュの直し |
   | formal（公用文、規程、契約書、仕様書） | 硬い漢語の言い換え（正式な語）、「〜を行う」「〜することができる」の言い換え |
   | promo（紹介記事・宣伝文） | 見出しのキャッチコピー、「！」と絵文字、勢いのある語と強める語、評価の語を短く重ねる型の直し（「紹介記事・宣伝文の勢い」） |
   | mail（メール・チャット） | 宛名、挨拶、結び、署名、クッション言葉の削り、敬語の度合いと口語の書き換え、絵文字の削除 |
   | paper（論文・研究レポート） | ぼかした語の具体化（慎重な言い方）、専門用語と論文調（本研究では）の言い換え、長い文の分割、名詞化の言い換え |

## PR説明（pr）

あわせて読む: 「業務・仕様・実務ドキュメント向け仕様」

### 1. 普通な書き方（直さない）

- 変更点と確認したことの箇条書き、チェックリスト、体言止めの項目（「期限切れのキャッシュを削除する処理を追加」）。
- テンプレートの見出し（概要、変更点、テスト、確認したこと）。見出しの数と順は変えない。
- 識別子が主語の文（`retry_limit` が再試行の上限を決める）。読者が expert か informed なら直さない（「文書の種類と読者」の7章）。
- 既定の読者の目安は expert（レビューする開発者）。

### 2. それでも直すもの

- 変更報告の述語の抜けと、実施済みと予定の取り違え（SKILL.md「文書の立場と文末」）。
- 確認したことと確認していないことを混ぜた文。確認していない動作を確認済みと書かない。
- 「- **改善点**: 〜を改善しました」のように、ラベルとコロンで説明の文を並べるだけの箇条書き（太字でなくても同じ）。

### 3. 長さと省略

- 1つの箇条に1つの変更を保つ。箇条書きを地の文にまとめない。
- 体言止めの項目を文にのばさない。

### 4. 例（合成）

| 元 | 扱い |
|---|---|
| - 期限切れのキャッシュを削除する処理を追加 | 残す（体言止めの変更点） |
| - **改善点**: 一覧の表示を改善しました | ラベルを外し、「一覧の表示を改善しました」のように述語まで書く。何をどう変えたかは、原文と資料にあるときだけ書く |

## 技術記事（article）

あわせて読む: 「技術記事・エンジニア発信向け仕様」

### 1. 普通な書き方（直さない）

- コードの囲みとその説明、項目名の見出し、並列が明確な手順の箇条書き。
- 原文の常体か敬体。技術記事という理由だけで敬体にしない（SKILL.md「文書の立場と文末」）。
- 対象読者、前提、参照先を示す文（「この記事は、Python を使ったことがある人を対象にしています」）。

### 2. それでも直すもの

- SKILL.md「1. 基本原則」のとおり。この種類で外す規則はない。
- 続く内容を予告するだけの導入（「本記事では〜をご紹介します」）と、書き手がAIに出した指示の残り（`references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の6章）。

### 3. 長さと省略

- 読者の段階に従う（「文書の種類と読者」の9章）。
- コードの囲みの中、コマンド、識別子は変えない。

### 4. 例（合成）

| 元 | 扱い |
|---|---|
| この記事は、Git の基本操作を知っている人を対象にしています。 | 残す（対象読者を示す案内） |
| 今回はあえて理論には触れず、手を動かす部分だけを書きます。 | 書き手の方針を述べるだけなら削る。読者に範囲を知らせる案内として要るなら残す |

## 障害報告（incident）

あわせて読む: 「業務・仕様・実務ドキュメント向け仕様」

### 1. 普通な書き方（直さない）

- 時刻と事象の箇条書きか表、体言止めの経過（「10:05 復旧」）。
- 「発生」「復旧」「影響範囲」「暫定対応」のような報告の語。ふだんの言葉に開きすぎない。
- 伝聞の「〜とのこと」、調査中の原因を調査中と書く文。
- 再発防止の決意の結び（内容を残し、大げさな語だけを直す。SKILL.md「最優先ルール: 意味の保持」）。

### 2. それでも直すもの

- 調査中の原因を言い切る直し、伝聞や確度の変化（〜とのこと を断定にする）。
- 時刻の取り違え（見聞きした時刻と、出来事が起きた時刻）。
- 結びの大げさな語（全社一丸となって、など）。結びの内容は残す。

### 3. 長さと省略

- 経過の体言止めの項目と「〜とのこと」を残す。時系列の順を変えない。
- 社内向けかお客さま向けかは、読み手との関係を指定されたときに決める（「書き手と読み手（ペルソナ）」）。段階が informed か general の読み手には、社内の呼び名、管理番号、ホスト名に説明が要る所を返す。社外の読み手でも、書き手の作業の文は丁寧語のままにし、原因の確度と時系列を変えない（「書き手と読み手（ペルソナ）」の8章）。

### 4. 例（合成）

| 元 | 扱い |
|---|---|
| - 09:40 決済の失敗が増加 | 残す（時系列の体言止め） |
| 原因はキャッシュの設定とのことです。 | 残す（伝聞のまま。「原因はキャッシュの設定です」にしない） |

## 提案書（proposal）

あわせて読む: 「業務・仕様・実務ドキュメント向け仕様」

### 1. 普通な書き方（直さない）

- 結論や提案を先に置いた構成。
- 論点や費用の箇条書き。
- 「ご判断ください」「ご承認をお願いします」のように判断を求める文。

### 2. それでも直すもの

- 効果の見込みを強める直しと、元にない効果を足すこと（業務効率が大きく向上します、など）。
- 判断を求める強さの変化。依頼、相談、提案、決定を取り違えない（「業務・仕様・実務ドキュメント向け仕様」の2章）。
- 読み手（上司、決裁者）が決める事柄を決まった形で書いた文は、書き手と読み手を指定されたとき知らせる。書き手が決められる立場（リーダーからチームへ）の文と、案と分かる文は知らせない（「書き手と読み手（ペルソナ）」の5章）。

### 3. 長さと省略

- 推敲では構成を組み替えない。結論を前に出す直しもしない。
- 費用、期間、条件の数値と、その掛かる範囲を保つ。

### 4. 例（合成）

| 元 | 扱い |
|---|---|
| 導入により、問い合わせ対応が楽になる見込みです。 | 「見込みです」の確度を保つ。「楽になります」と言い切らない |
| 来週の定例でご判断ください。 | 残す（判断を求める依頼の文） |

## 議事録（minutes）

あわせて読む: 「業務・仕様・実務ドキュメント向け仕様」

### 1. 普通な書き方（直さない）

- 項目に分けた構造と、体言止めの項目。
- 「**日時**: 10月1日」「**出席者**: 3名」のようなラベルと値。
- 同じ文末の連続（「〜しました。〜しました。」）と、伝聞の「〜とのこと」。
- 既定の読者の目安は expert（会議の出席者）。

### 2. それでも直すもの

- 発言者、作業した人、担当を引き受けた人の取り違え（「業務・仕様・実務ドキュメント向け仕様」の2章）。
- 元にない決定、ToDo、「決定なし」の記載。担当が書かれていないことを「担当未定」と決めること。

### 3. 長さと省略

- 話題の順と見出しの扱い（推敲では変えない。新しく作るときだけ話題ごとに整理してよい）は 「業務・仕様・実務ドキュメント向け仕様」の3章。
- 体言止めの項目を文にのばさない。

### 4. 例（合成）

| 元 | 扱い |
|---|---|
| - 次回日程: 未定 | 残す（ラベルと値。原文の「未定」も残す） |
| 山田さんから進捗の報告がありました。資料の修正は佐藤さんが引き受けました。 | 残す（報告した人と引き受けた人を分けて書いている） |

## マニュアル（manual）

あわせて読む: 「技術記事・エンジニア発信向け仕様」 か 「業務・仕様・実務ドキュメント向け仕様」（中身で選ぶ）

### 1. 普通な書き方（直さない）

- 番号つきの手順と、1手順1動作。
- 「〜してください」の連続と、注意や警告の欄。
- かぎ括弧の画面の項目名（「保存」ボタン）。
- 読者のために扱う範囲を示す文（「この手順書では、退職の手続きは扱いません」）。AIへの指示の残り（`references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の6章）の残す例に当たる。
- 部下・後輩の読み手でも、敬語を下げない（利用者が頼んだときだけ。「書き手と読み手（ペルソナ）」の7章）。

### 2. それでも直すもの

- 手順の中の条件の掛かり方のずれ（どの手順に「〜の場合だけ」が掛かるか）。
- 警告や必須の指示を弱める直し。
- 先に済ませる作業や依頼を括弧に入れた文。括弧から出して、行う順に文で並べる（SKILL.md「Step 2: 文章の書き直し」の5）。手順の番号と数は変えない。

### 3. 長さと省略

- 手順の数と順を変えない。文を分けても手順は分けない。
- 文書の立場は多くが決まりだが、種類から立場を決めない。

### 4. 例（合成）

| 元 | 扱い |
|---|---|
| 3. 「保存」を押してください。 | 残す（1手順1動作。画面の項目名） |
| 4. 設定を確認し、問題がなければ再起動してください。 | 残す（条件が再起動だけに掛かる。手順を2つに分けない） |

## スライド（slides）

あわせて読む: 「技術記事・エンジニア発信向け仕様」 か 「業務・仕様・実務ドキュメント向け仕様」（中身で選ぶ）

### 1. 普通な書き方（直さない）

- 短い句や体言止めの見出しと箇条書き、ラベルと値の項目。
- 目次と「ポイントは3つです」、まとめのページ。
- 箇条で強調として選んだ「〜のは、A、B、C」の形。
- `---` のページの区切り、Marp などの先頭の設定、話者のノート。

### 2. それでも直すもの

- 長い文の見出し。何を扱うページかが分かる短い項目名にする（SKILL.md「案内用の見出し」）。
- 縮めすぎた標語の見出し。補い方が1つに決まるときだけ補い、決まらなければ残して確かめる。
- 「速い。軽い。安い。」の型と絵文字。

### 3. 長さと省略

- ページの数と順、ページの中の項目の順を変えない。説明の文をページに足さない。
- 1つの箇条は1行に収まる長さを保つ。体言止めと助詞の省略を残し、文にのばさない。
- 見出しの印がない文字（PowerPoint から写したもの）には見出しの規則を当てない。
- 新規作成では、スライドに番号を付ける。

### 4. 例（合成）

| 元 | 扱い |
|---|---|
| - キャッシュの期限を短縮 | 残す（体言止めの項目。「短縮しました。」にしない） |
| ## ポイントは3つです | 残す（目次のページ） |
| ## 速さは、信頼。 | 直す候補。何を扱うページかが分かる見出しに戻す。補い方が1つに決まらなければ直さずに確かめる |

## エッセイ・小説（essay）

あわせて読む: 「エッセイ・オピニオン・個人発信向け仕様」

### 1. 普通な書き方（直さない）

- エッセイ: 書き手の語り、話し言葉、気持ちの語、体験の順。何を何に例えたかが読み取れる比喩は、字義どおりでなくても書き手の個性として残す。
- 小説の本文: 会話、読み取れる比喩、短い文の連続、ダッシュ、三点リーダー、語り手の主観、書き手が残した複数の読み（SKILL.md「最優先ルール: 意味の保持」）。

### 2. それでも直すもの

- 主語と述語だけを取り出すと成り立たず、連想もできない比喩と、動作と主語が釣り合わない比喩。エッセイでも小説でも直す（目印は `references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の8章）。直すときは前後の文から分かる様子だけで書き、分からなければ原文を残して「書き手に確かめたい点」で尋ねる。
- 係り方がずれて、文として通らないもの（4章の例）。
- 否定と肯定を2文に分けた否定対比（「Xではない。Yだ。」）。否定を残して1文にまとめる（SKILL.md「セルフラベリングと否定対比の整理」）。小説の語りと会話で、書き手が文体として短い文を重ねている箇所は1章のとおり残す。
- エッセイの比喩動詞（`references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の1章の表の動詞を比喩に使ったもの。「効く」「溶かす」の類。直し方は SKILL.md「比喩動詞の具体化」）。定着した言い方は残す。
- 小説でも、絵文字、チャット応答の名残、本文に残ったAIへの指示は直す。
- 直した案が、効き目をぼんやり述べる形や、`references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の8章の目印の形（物や場所が「黙って〜している」など）になるなら、案を捨てて原文を残す。

### 3. 長さと省略

- 平均の文長の目安を使わず、書き手の文のリズムを残す。
- 小説の本文には、コピー調と装飾記号のダッシュの規則と、「エッセイ・オピニオン・個人発信向け仕様」 の教訓や情緒語を見直す項目を当てない。
- 比喩は前後の文と合わせて見る。あとの文で例えた理由を説明している比喩は残す。
- ペルソナで本文を変えない（敬語を上げない、揺れをそろえない、主語を補わない）。ペルソナの知らせ（知りえない事情、断定、合わない言い方）も出さない（「書き手と読み手（ペルソナ）」の8章）。
- 比喩や語りを個性として残したときは、確認の記録の下に1行、「エッセイと判断したので、文の個性を残しました」（小説なら「小説と判断したので、読み取れる比喩と語りを残しました」）と書く。直した箇所があっても書く。本文だけを返す指定では書かない。
- 会話やファイルからは事実を補わず、事実の問いも出さない。

### 4. 例（合成）

| 元 | 扱い |
|---|---|
| 寝つきが悪かった。散歩を始めてから、じわじわ効いてきた。（エッセイ） | 何がどう変わったかを書く（散歩を始めてから、少しずつ寝つきがよくなってきた）。前後から変わったことが分からなければ、定着した言い方にする |
| 引っ越しの段ボールは、渡り鳥の群れのように、部屋の隅から隅へと移っていった。（エッセイ） | 残す（何を何に例えたかが読み取れる。書き手の個性） |
| 彼のつぶやきは、冷えた窓ガラスに白い輪を残して消えた。（小説） | 残す（息で窓ガラスが白く曇る様子と読める） |
| 封筒の封を切った瞬間、台所の午後が、そっと膝を抱えた。（小説） | 直す（「午後が膝を抱える」は何を言うかを連想できない）。前後の文から分かる様子で書き、分からなければ確かめる |
| 湯気があまりに心地よくて、握った手すりのほうが、先にゆるんでいく。（小説） | 直す（湯気があまりに心地よくて、手すりを握る指のほうが、先にゆるんでいく） |

## 公用文、規程、契約書、仕様書（formal）

あわせて読む: 「業務・仕様・実務ドキュメント向け仕様」 か 「技術記事・エンジニア発信向け仕様」（中身で選ぶ）

### 1. 普通な書き方（直さない）

- 正式な漢語と定義された語（実施する、行う、届出、甲、乙）。和語に言い換えない。
- 義務の語（しなければならない）、権限の語（することができる）、許可の語（してよい、差し支えない）、努力の語（努めるものとする）と、「〜するものとする」「〜とする」の文末。
- 条文の形（第1条、項、号）、定義の条、ただし書き、長い条件の文。
- 「〜に関して」「〜を実施」のような名詞化の言い回し（`references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の7章の名詞化の言い回し）。

### 2. それでも直すもの

- 絵文字、チャット応答の名残、本文に残ったAIへの指示、定型の結び（`references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の6章）。
- 根拠のない誇張（飛躍的、画期的）と、意味のぼやけた流行語。正式な用語ではないので、ほかの種類と同じに扱う。
- 条件や例外がどの項や動作に掛かるかが読み取りにくい文。掛かる先が1つに決まるときだけ直し、決まらなければ確かめる。

### 3. 長さと省略

- 条、項、号の数と順と番号を変えない。条文を分けたりつないだりしない。
- 数値、期日、期間、金額と、それが掛かる範囲を変えない。
- 許可（〜してよい）、能力・権限（〜できる）、説明（〜する）、保証（必ず〜する、〜を保証する）は仕様の違いなので、互いに替えない。「〜場合がある」は言い切らず、説明に「必ず」「保証する」を足さない。
- 多くは決まりの文書だが、立場は種類ではなく本文の手がかりで決める（SKILL.md「文書の立場と文末」）。
- 会話やファイルからは事実を補わない。

### 4. 例（合成）

| 元 | 扱い |
|---|---|
| 申請者は、住所を変更したときは、14日以内に届出を行わなければならない。 | 残す（義務の語、期間、「届出を行う」は規程の言い方） |
| この契約の期間は、2027年4月1日から1年間とする。 | 残す（期日と期間、「〜とする」を変えない） |
| 本システムは、利用者の利便性を飛躍的に向上させる画期的な仕組みである。 | 誇張の語を直す候補（`references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の7章）。元にない効果や数値は足さない |

## 紹介記事・宣伝文（promo）

あわせて読む: 「エッセイ・オピニオン・個人発信向け仕様」 か 「業務・仕様・実務ドキュメント向け仕様」（個人の記事はエッセイの節、店や会社の宣伝文は業務の節）

### 1. 普通な書き方（直さない）

商品、お店、場所、サービス、作品を勧める記事と宣伝文では、書き手の勢いが記事の魅力そのものになる。技術文書やヘルプと同じ直し方をすると、その魅力を削る。

- 「！」: 消さず、読点にも変えない。同じ段落に3つ以上並んでも減らさない。
- 見出しのキャッチコピー: 短い項目名にする直し（SKILL.md「案内用の見出し」「コピー調の抑制」）を当てない。言い回しを本文へ移しても、見出しで読者を引きつける働きは戻らない。見出しとして書かれた番号つき項目の行（1. 昭和から愛される…）と太字だけの行も同じに扱う。
- 本文で評価の語を短く重ねる型（安い。うまい。早い。）も勢いとして残す。対象と評価を1文につなぐ直し（SKILL.md「コピー調の抑制」）を当てない。
- 勢いのある語（パンチ、大活躍、最強、イチオシ、抜群）: 「力強い風味」「重宝」のような落ち着いた言い方に置き換えない（`references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の7章の硬い漢語と誇張語の行を当てない）。
- 強める語（本当に、ぜひ、ずらりと）: 気持ちや量の強さを表すので削らない。「ぜひ〜してみてください」も書き手の実際の勧めとして残す。
- 同じ褒め言葉の繰り返し（1段落に「絶品」が3回）: 勢いとして残す。並んだ対象を1文にまとめず、回数を減らさず、ほかの語にも置き換えない。元にない褒め言葉は足さない。
- 「エッセイ・オピニオン・個人発信向け仕様」 の「過剰な修飾語を削る」と、「業務・仕様・実務ドキュメント向け仕様」 の「過剰な装飾を減らす」「自然で客観的な表現」は、勢いのある語と強める語に当てない。
- 絵文字: 書き手が気持ちや勢いを表すために使ったものは残す。
- 「〇選」「おすすめ」の見出し、ランキングや一覧の形、価格や購入先の案内。

### 2. それでも直すもの

勢いを残すことは、読みにくさを残す理由にならない。

- 誤字と脱字。表記の揺れをそろえるのは、ほかの種類と同じく表記の校正に任せる（SKILL.md「用途と表記の扱い」）。
- 主語と述語が噛み合わない文、係り先の分からない文。見出しも、事実の誤りや主述のずれがあるときだけ直す。
- 根拠のない誇張が事実のように書かれている所（「県内でいちばん売れている」「誰もが絶賛」）。yomiyasu-mini は事実を確かめられないので、書き換えずに「書き手に確かめたい点」で根拠を尋ねる（本文を確定するのに要る確認として、確かめたい点の3点の中に数える）。

### 3. 長さと省略

- 見出しの数と順、一覧の項目の数と順、価格、商品名、店名、購入先は変えない。
- ペルソナで本文を変えない（敬語を上げない、主語を補わない）。ペルソナの知らせ（知りえない事情、断定、合わない言い方）も出さない（「書き手と読み手（ペルソナ）」の8章）。
- 1章の勢いのある書き方（見出しの言い回し、「！」、勢いのある語など）を残したときは、本文とは別に、利用者への補足として確認の記録の下に1行、「紹介記事・宣伝文と判断したので、勢いのある書き方を残しました」と書く（「エッセイ・小説（essay）」の3章と同じ形）。直した箇所があっても書く。本文だけを返す指定のときは書かない。
- 会話やファイルからは事実を補わない。新しい問いは出さず、2章の根拠のない誇張だけを尋ねる。

### 4. 例（合成）

| 元 | 扱い |
|---|---|
| 港町のスーパーで探す最強のお土産！安くて美味いご当地ラーメン4選 | 残す。「最強のお土産、」のように「！」を読点に変えない |
| 1. 昭和から愛される港町のソウルフード「しおかぜラーメン」（なぎさ製麺） | 残す。「1. しおかぜラーメン（なぎさ製麺）」に縮めない |
| 2. 焦がしニンニク油が香る本格派「灯台とんこつラーメン」（なぎさ製麺） | 残す。「2. 灯台とんこつラーメン（なぎさ製麺）」に縮めない |
| 焦がしニンニク油のパンチを自宅で味わうなら | 残す。「力強い風味」にしない |
| 自宅用にも配り用にも大活躍するおすすめ銘柄 | 残す。「重宝する」にしない |
| 港町の駅前にある食堂の日替わり定食。安い。うまい。早い。 | 残す。「この定食は安く、うまく、早い。」のように1文につながない |
| スープは濃厚！麺はもちもち！しおかぜラーメン、本当におすすめです！ | 残す。同じ段落に「！」が3つ以上並んでも減らさず、読点にも変えない |
| この麺は絶品です。スープも絶品で、具も絶品です。 | 残す。「この麺もスープも具も絶品です。」のように1文にまとめず、「絶品」を減らさない |
| どこの店より安い、県内でいちばん売れているお土産です！ | 本文は変えず、「書き手に確かめたい点」で「どこの店より安い」「いちばん売れている」の根拠を尋ねる |

## メール・チャット（mail）

あわせて読む: 「業務・仕様・実務ドキュメント向け仕様」

### 1. 普通な書き方（直さない）

社内外のメールと、Slack などのチャットの投稿。宛名、挨拶、署名、結びの言葉は、相手との関係を保つための書き方で、決まり文句として削らない。これらと敬語の度合いを残したことと、残した理由は、返答に書かない（この文書の「書き手と読み手（ペルソナ）」）。

- 宛名（〇〇様、〇〇さん、各位）、挨拶（お世話になっております、お疲れさまです）、結び（よろしくお願いいたします）、署名。`references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の6章の「定型の結び」と「チャット応答の名残」を、相手への実際の返信と結びには当てない。
- 敬語の度合い。「〜いただけますでしょうか」を「〜してください」にせず、逆に「〜して」を「〜していただけますか」にもしない。頼みの強さと丁寧さは書き手が相手に合わせて選んだもの。書き手と読み手との関係を依頼で言われたときは、敬語と社外の相手に向けた言い回しは 「書き手と読み手（ペルソナ）」の7章の範囲で上げる（この項より先に当てる）。
- クッション言葉（お手数ですが、恐れ入りますが）。相手への配慮なので削らない。
- チャットの口語（〜かも、〜しときます、〜っす）。「です・ます」にそろえず、書き言葉にも直さない。
- 書き手が気持ちを表すために使った絵文字と「！」。
- 挨拶、頼み、結びの文末に「ます」が続くこと。決まり文句の文末を書き換えて散らさない。

### 2. それでも直すもの

- 誤字、脱字、敬語の誤り。二重敬語や、「ご〜する」に「させていただく」を重ねた形（ご確認させていただきました）は、敬語の度合いを保ったまま直す（確認いたしました）。尊敬語と謙譲語の取り違え（資料を拝見してください → 資料をご覧ください）も直す。
- 何を頼んでいるのかが分からない文と、主語と述語が噛み合わない文。
- 1文に頼みごとが2つ以上混ざっていて、どちらに返事をすればよいか分からない文。頼みごとごとに文を分ける。分け方が1つに決まらないとき（期限がどちらの頼みに掛かるか分からないなど）は書き換えず、「書き手に確かめたい点」で尋ねる。
- 同じ詫びや礼が3回以上並ぶ所。このときだけ減らしてよい。1つは残し、「変えたところ」に書く。2回までは残す。
- 本文に残ったAIへの指示（`references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の6章）。

### 3. 長さと省略

- 頼みごと、期限、数字、日時、金額、固有名詞、URL、メールアドレスは一字も変えない。期限を「中旬」「目安」のようにぼかさない。
- 短くしすぎない。挨拶やクッション言葉を削って用件だけにしない。

### 4. 例（合成）

| 元 | 扱い |
|---|---|
| お手数ですが、10月20日までにご確認いただけますでしょうか。 | 残す（クッション言葉、敬語の度合い、日付） |
| それ明日でもいいかも、確認しときます | 残す（チャットの口語。「です・ます」にしない） |
| ご確認させていただきましたところ、問題ございませんでした。 | 直す（確認いたしましたところ、問題ございませんでした。）。敬語の度合いは変えない |
| 山本様、お世話になっております。先日お送りした見積もりは、いかがでしたでしょうか。 | 残す（宛名と挨拶。「いかがでしたでしょうか」は相手への実際の問い） |
| 見積書の送付と、打ち合わせの日程の調整を、金曜までにお願いできますか。 | 「金曜まで」が両方に掛かるか、日程の調整だけに掛かるかが決まらないので書き換えず、書き手に確かめる |

## 論文・研究レポート（paper）

あわせて読む: 「技術記事・エンジニア発信向け仕様」

### 1. 普通な書き方（直さない）

論文、学会の予稿、卒業論文、研究レポート、調査報告。主張の確かさの度合い、引用、数値は、書き手が根拠に合わせて決めたもの。

- 慎重な言い方（と考えられる、と思われる、可能性がある、示唆する、推測される、の範囲では、かもしれない）。「〜である」「〜を示す」の断定に変えない。逆に、断定を弱めることもしない。
- 引用の印（[1]、[2, 5]、(山田 2020)、(Smith et al., 2019)）、数値、単位、有意水準、統計の値（SD = 3.1、p < .05）。一字も変えない。引用の印を別の文や句へ動かさない（どの主張を支える引用かが変わる）。
- 専門用語。読者を general と指定されても言い換えず、本文に説明も足さない（「文書の種類と読者」の8章の言い換えより、この種類の決まりを優先する）。
- 「である」調。「です・ます」に変えない。そろえるのは、地の文で2つが混ざっているときだけ。
- 「本研究では」「先行研究」と、「考察」「結論」などの見出し。「技術記事・エンジニア発信向け仕様」の3章の、過度な論文調を削る項目を当てない。
- 条件と結果が1文にまとまっているほうが正確な長い文。SKILL.md「文長と読点の調整」の平均の目安で分けない。
- 名詞化の言い回しと正式な漢語（〜の実施、〜に関して、調査を行った）。`references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の7章の名詞化の行のとおり残す。

### 2. それでも直すもの

- 誤字と脱字。同じ用語の表記の揺れをそろえるのは、ほかの種類と同じく表記の校正に任せる（SKILL.md「用途と表記の扱い」）。書き方の違いで別の概念と読めるおそれがあるときは、そろえずに「書き手に確かめたい点」で尋ねる。
- 係り先が分からない文と、主語と述語が噛み合わない文。長い文を分けるのはこのときだけで、係り先が1つに決まるときに限る。
- 「の」が4つ以上続く所。語順を変えるか、「の」の1つを内容に合う助詞や動詞にする。意味が1つに決まらなければ残す。
- 同じ文末が3文以上続く所。語順や文のまとめ方で整える。文末の種類を変えて散らさない（慎重な言い方を断定にしない。「である」を「です」にしない）。
- 本文に残ったAIへの指示と、データや出典に基づかない誇張（`references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の6章、7章）。読者のために扱う範囲や前提を示す文は残す。

### 3. 長さと省略

- 見出し、節、図表、引用文献の数と順と番号を変えない。
- 数値と単位、統計の値、引用の印と、それが掛かる主張の範囲を変えない。
- 会話やファイルからは事実を補わない。

### 4. 例（合成）

| 元 | 扱い |
|---|---|
| この結果は、AとBの間に関係がある可能性を示唆する。 | 残す（「関係がある」「関係を示す」にしない） |
| 平均は12.4（SD = 3.1, p < .05）であった [3]。 | 残す（数値、記号、引用の印を一字も変えない） |
| 本研究では、40名の参加者を対象に聞き取りの調査を行った。 | 残す（「本研究では」と「調査を行った」は論文の言い方） |
| 今回の調査の範囲では、両群の間に差は見られなかった。 | 残す（「の範囲では」を消すと、調べていない所まで差がないと言うことになる） |
| 室温が25度を超え、かつ湿度が70%以上の条件でのみ、反応時間の増加が見られた。 | 残す（条件と結果を1文に保つ。分けると「のみ」が掛かる範囲がぼやける） |
| 本実験の結果の傾向の分析の手順は付録に示す。 | 直す（本実験の結果の傾向を分析した手順は、付録に示す。） |

## 技術記事・エンジニア発信向け仕様

技術記事では、手順や仕組みの説明を読み手が追えるように書きます。
過剰な装飾を減らし、元の文や資料で分かる範囲で手順や設定を整理します。

---

### 1. 装飾と箇条書きの整理

#### 太字と箇条書きの制限
太字は1,000文字あたり1〜2箇所までに抑え、段落内に複数の太字を乱発しません。残す太字は、かっこの内側だけを太字にするなど、表示される書き方に整えます（SKILL.md「装飾記号の排除と太字の表示」）。
箇条書きは、独立した変更点、手順、担当と結果の対応など、並列関係が明確で読みやすい場合はそのまま残します。全体の15%以下という数値は過剰な箇条書きを見直す目安であり、機械的な上限ではありません。AI調に見えるという印象や比率の数値だけで、伝わりやすいリストを無理に地の文へ戻さないでください。
一方、思考の流れや論理関係が箇条書きによって不自然に分断されている場合は、地の文の段落に統合します。統合する際は、各項目を文書の立場に合う文末にし（SKILL.md「文書の立場と文末」）、元にない評価や義務（〜が大切です、〜する必要があります等）を足しません。なお、地の文に直すと同一文末が単調に続くようなときは、箇条書きのまま維持します。

#### 装飾記号と定型構成の排除
見出しや本文に絵文字は使いません。装飾としての文末コロン（：）やダッシュ記号（「—」や罫線「─」「━」「──」）も除きます。Qiitaの調査では「まとめ」見出しを含む記事が50%以上ありました。短い記事で本文を繰り返すだけの「まとめ」見出しと段落は置きません。削るときは、まとめの中にしかない数値・条件・例外を落としません。

---

### 2. 手順と設定を分かりやすくする

抽象的な概念説明にとどまらず、元の文や前後の資料にある情報の範囲で手順や設定を整理します。読者の理解に必要な定義、識別子、値と状態の対応が依頼や資料で提供されている場合は、説明に活かします。文脈にない前提や原因、コマンドやコード片を推測で創作したり、条件や挙動を勝手に書き換えたりしません（失敗時に値を代入しない処理をfalse代入に変えない等）。

SKILL.md「Step 1: 文脈と段落の把握」の文の構造の点検に従い、仕様の条件・例外・否定・限定が掛かる処理と、分岐・手順の順序を確かめます。語順の整理や文の分割を行っても、条件を別の処理へ広げたり、必要な用語の対応を崩したりしません。

| 不自然な比喩表現 | 客観的・具体的な記述への変換 |
|---|---|
| 設定を保存した瞬間に、古いキャッシュが静かに壊れます。 | 設定を保存するとすぐに、古いキャッシュが気づかないうちに使えなくなります。 |
| この調整が、検索の速さに地味に効いてきます。 | この調整が検索の速さに目立たないながらも役立ってきます。 |
| 原因調査に丸一日溶かしてしまいました。 | 原因の調査に丸一日かかってしまいました。 |
| この処理でデータの整合性を担保します。 | この処理でデータに矛盾が生じない状態を保ちます。 |

---

### 3. 文体

常体・敬体は、変更の指定がない限り原文を保ちます。技術記事という理由だけで敬体へ変えません。同一文末の連続は見直すきっかけにとどめ、語尾を散らすために文の働きを変えません。同じ意味の変更動詞が隣り合って単調な場合は、語順や文のまとめ方も考えますが、語尾を散らす目的で文の働きや時制を崩さないようにします。書き直しで新たに呼びかけを増やした場合は、各節の働きと文体変更の必要性を再確認します。
敬体にすることと、すべての動作を「〜します」にすることは別です。実施済みの変更報告、現在の動作・方針、今後の予定を時制と役割に沿って書き分けます。完了した変更の報告を予定のような「〜します」にしません。文脈から分かる主体（動作主）を必要な位置で示しつつ、元にない担当者の創作やシステム動作の過度な擬人化は避けます。読み手への設計助言と、定められた手順、書き手の予定、道具の働きの説明を区別し、SKILL.md「文書の立場と文末」に従います。
「本稿では」「筆者は」といった過度な論文調や、冒頭の空疎な前置き（「近年、AI技術の発展は目覚ましく…」など）を削り、解決すべき課題や前提条件から書き始めます。
「本記事では〜をご紹介します」「それでは見ていきましょう」のように、続く見出しや本文の内容を予告するだけの導入や進行説明も削ります。対象読者や前提、長い手順書の構成など、本文にない案内を担う文は残します。
難しい漢語が続く箇所は、ふだん使う言葉や動詞に直します（意味の幅が同じで、目的語が追える言葉にします）。専門的な意味で使う語は、SKILL.md「専門用語と名称の扱い」に従い、定着した用語と名称の対応を保ちます。漢字の割合は20%前後を目安にします。ソフトウェアのversionを「版」、regressionを「回帰」とした直訳は、開発現場で定着している「バージョン」「リグレッション」「デグレ」や具体的な説明へ直します。出版物の「改訂版」や「回帰テスト」など定着した言い方は残します。

## 業務・仕様・実務ドキュメント向け仕様（PR / 仕様書 / 社内レポート / 提案書）

業務文書は責任の所在や判断の基準が読み手に伝わるように書きます。
元の意味と条件を保ち、以下の指針に従って整えます。

---

### 1. 比喩をふだんの言葉に直す

意味を取り違えやすい比喩は、直接的でふだん使う言葉に書き換えます。比喩や言い回しが持っていた気持ちや評価の向き、理由は残します。
- 含みの例: 「うっかり」の不注意、「ようやく」の待ちくたびれた感じ、「〜てしまった」の後悔、「地味に」の目立たないけれど確かにある感じ。
- 比喩の語は言い換えて構いませんが、その語が伝えていた含みや理由は、別のふだんの言葉で補って言い表します。
- 比喩動詞だけでなく、副詞や前置きの言い回しも同じ扱いにします。
なお、「骨が折れる」「手を焼く」「目から鱗が落ちる」「首を長くして待つ」のような、ふだんの日本語で定着した慣用句は、AIっぽい比喩として扱わずそのまま残します。業務仕様でも、意味を取り違えるおそれがなければ残します。迷ったときの目安は、その言い方を、AIが広まる前の人の文章でもふつうに見かけるかどうかです。見かけるなら残します。
絵文字や装飾としての文末コロン（：）も使いません。

| 不自然な例（比喩・曖昧語） | 推奨表現（自然で客観的な表現） |
|---|---|
| 判断に迷ったときは、安全側に倒して判断します。 | 判断に迷ったときは、安全を優先して判断します。 |
| 前提の理解がずれていると、全体の設計が崩れやすくなります。 | 前提の理解がずれていると、全体の設計に問題が生じやすくなります。 |
| 新機能の手触り感を確認します。 | 新機能の使い勝手を確認します。 |
| 現状の課題について解像度を上げます。 | 現状の課題についてより詳しく整理します。 |
| 作業リソースを各工程へ配ります。 | 作業リソースを各工程へ割り当てます。 |

---

### 2. 条件・採否の基準・責任の所在を明確にする

#### 主語の明確化
受動態で曖昧になっている箇所は、元の文や前後の資料から主体が特定できる場合に限り、「開発チームで合意した」など責任主体を明記します。特定できない場合は無理に架空の人物や役職を作らず、自然なシステム動作を人間の行為に変えることも避けて、客観的な事実として記述します。
議事録やタスク一覧では、出席者、発言者、作業の実行者、担当を引き受けた人を区別し、原文や提供文脈にない担当を割り当てません。担当が書かれていないことを「担当未定」ともみなさず、担当の候補や予定はその強さのまま残し、原文や提供文脈から分かる実行者と作業の対応も保ちます。

#### 条件と結果の1対1対応
「適宜対応する」のような曖昧な表現は、元の資料にエラーコードや再試行回数などの条件がある場合だけ具体的に書きます。読者の理解に必要な定義、識別子、値と状態の対応が依頼や資料で提供されている場合は、説明に活かします。資料にない条件や数値を推測で創作したり、失敗時に値を代入しない処理をfalse代入に変えるような実際の動作・条件の改変は避けます。
独立した変更点や手順、担当と結果の対応など、並列関係が明確で読みやすい箇条書きは、AI調という印象や比率の都合だけで無理に地の文へ戻さず残します。

SKILL.md「Step 1: 文脈と段落の把握」の文の構造の点検に従い、期限や条件がどの対象・動作に掛かるかを確かめます。修飾や名詞の連続を整理しても、依頼・相談・提案・決定の区別と強さを保ちます。主体が分からない場合は、新しい担当者や責任を割り当てません。
相手との関係や書き手の希望が分かる依頼は、内容・条件・期限を保って語調を整えます。希望された「〜してもらえると助かります」などの依頼の定型と、新しい具体的な便益・感情・感謝の追加を分けます。定型を一律に追加・削除せず、期限を目安や都合次第にしません。安全手順や必須の指示を弱めません。

提出・共有する文では、原文の仮置きを見直します。入れる値が原文・依頼・提供資料に明示されている場合だけ置き換えます。必要な値が不明なら推測で埋めたり削ったりせず、確認欄を出す形式なら本文とは別に尋ねます。意図的なテンプレート、引用、画面や項目の名称は保ち、【】などの見た目だけで仮置きと決めません。

#### 不要な前置きと曖昧な表現の整理
「検討にあたっては多角的な視点を考慮し…」といった前置きを削り、結論や要請事項から書き始めます。ただし、比較結果から方針へ移る合図など、前後をつなぐ働きのある語は残します。主張だけでなく、説明・提案・決定の切替が読み手に伝わるか確かめます。
「境界」のように何を指すか曖昧な語がある場合も、推測で特定の責務・時点・問題へ限定せず、元にない事実を足さずに元の条件や主張と言い切りの強さを本文に残します。語の具体的な意味についての確認は本文に入れず、別に出します。

---

### 3. 文体

報告書、提案書、PR説明文では、過剰な装飾を減らし、内容とつながりを簡潔に書きます。文末を選ぶ前にまず文書全体で読み手に知らせる主たる用件を確かめ、その用件を果たすために各段落で伝える内容を決めます。変更報告では一般的な宣言の後に方針宣言を並べるのではなく、提供された事実をもとに「どの指針・設定・実装を、どう改めたか」を書き手の改定行為として述語まで書きます。変更したと分かる内容だけを改定として報告し、未提供の比較や追加を作らず、現在の動作・仕様・方針しか分からない記述を今回の変更や維持の方針へ勝手に変えません。現在の動作・仕様・方針を補足する場合も、何の現在の状態を説明しているか、既知の改定とどういう関係なのかが読み手に伝わるように書き分けます。現在の運用方針や設定済みの指示を説明するときは、作業予定に見える「〜します」ではなく、誰の方針かを確かめて「〜するようにしています」「〜する方針です」など主体と状態が読める形にします。システムの実動作（返します）、利用可能な機能（できます）、手順、依頼、将来計画とは区別し、「ようにしています」を一律の語尾にしません。現在の方針を今回新設・変更・維持した履歴や確実な性能、未知の主体は作らず、関係が不明なら無関係な項目を因果でつなげず、完了した変更を予定のような「〜します」にしたり、現在の実動作や仕様説明をすべて過去形に揃えたりしません。同じ意味の変更動詞が隣り合って単調な場合は語順やまとめ方も工夫しますが、語尾を散らす目的で文の働きや時制を変えません。
「これらを理解すれば業務効率が飛躍的に向上します」のように、原文にない読了効果を付け足す表現は削除します。
短い文書で本文を繰り返すだけの「まとめ」見出しと段落は置きません。結論を先に示す構成や長い報告書の要約は残し、削るときもまとめの中にしかない数値・条件・例外・期限を落としません。
議事録を推敲するときは、話題の順と見出しを変えません。散文の記録を項目に分けるのはかまいません。話題ごとにまとめて並べ替えるのは、会議のメモから新しく作るときだけです。
共有用の議事録は、形式の指定がなければ、話題ごとの状況や確認事項を探せる短い項目に整理します。話題ごとにまとめて並べ替える場合も、事実、誰の報告・作業・提案か、賛否、合意の範囲、期限と条件、同じ話題の中で判断が変わった経過を保ちます。項目に分けることと情報を省く要約は区別し、発言順や逐語記録の指定があれば従います。原文にない決定事項やToDoの固定欄、「決定なし」などの記載は作りません。

## エッセイ・オピニオン・個人発信向け仕様（note / 個人ブログ）

エッセイでは、大げさな教訓や難しい熟語を減らし、書き手の素直な実感や感情を残します。
原文にある書き手の視点や生活実感を保ち、自然な文章に整えます。

---

### 1. 体験を大げさな教訓にしない

個人の日常の小さな発見や買い物の感想を、過剰に教訓化しません。すべてのエピソードに無理な教訓をつけず、「美味しかった」「面白かった」「疲れた」といった素直な実感を大切にします。

| 見直したい熟語 | 大げさな表現の例 | 自然な表現 |
|---|---|---|
| `真理` `虚飾` `境地` `美学` `深淵` `冷徹` `禁欲的` `優美` `極致` `宿命` | 日常の喧騒という虚飾を剥ぎ取った時、一杯のコーヒーに込められた真実が見えてくる。 | 日々の忙しさから離れたとき、一杯のコーヒーの本当の良さが見えてくる。 |

---

### 2. 生活実感と書き手の視点を保つ

#### 書き手の視点と感情
過度な一般論や大げさな教訓を避け、書き手の素直な視点を大切にします。「〜かもしれない」のような推量の強さも保ちます。客観的な説明文を勝手に個人の日記のような文体へ作り替えません。

#### 誇張のない素朴な描写
「深淵」「極致」といった過剰な修飾語を削り、元の文にある素朴な体験や感情を平易な言葉で表します。元の文にない五感の描写（冷房の温度や周囲の音など）を勝手に創作して足すことはしません。
「そっと」「寄り添う」「向き合う」「背中を押す」のような情緒語が、具体的な場面のないまま並ぶ場合は、元の文にある場面や行動で書き、語が伝えていた気持ちは残します。元の文に場面がなければ作り足さずに元の語を残します。「ドアをそっと閉める」のような動作の描写や、書き手が実感として使っている語は、情緒語であることだけを理由に変えません。

SKILL.md「Step 1: 文脈と段落の把握」の文の構造の点検に従い、出来事・観察・感情・推測の順を確かめます。語順の整理や文の分割を行っても、後から分かったことを最初から知っていたことにせず、未確定の原因を確定した説明へ変えません。出来事、観察、感情、推測の働きと時制を保ち、語尾の重複を避けるためだけに文の働きを変えません。また、並列関係が明確で読みやすい箇条書きがある場合も、AI調という印象だけで無理に地の文へ直さず維持します。

行動や感覚を描いた直後に、理由や解釈の候補を並べて「分からない」で締める内面の説明が場面ごとに繰り返される場合は、削ると書き手が描いた迷いまで消えるため、本文は変えません。「残したAIっぽいところ」に1行で挙げ、削るかどうかは書き手に任せます。

---

### 3. 文体

文の意味や働きを担わない定型の結び（`〜してみてはいかがでしょうか`、`ぜひ参考にしてみてください`、`いかがでしたでしょうか`）は使いません。紹介記事・宣伝文で書き手が実際に勧めている「ぜひ〜」は残します（「紹介記事・宣伝文（promo）」）。
「あなたも〜していませんか？」のような読み手への問いかけが何度も続く場合は、一つを残し、ほかは問いの内容を保って地の文にします。地の文にするときは、原文にない「多くの人が〜」のような一般化や書き手の経験を足さず、そう書けなければ問いかけのまま残します。手紙のように特定の相手へ語りかける文章や、読み手に実際に答えを求めている問いも残します。
最後の段落で無理やり社会や未来への提言を置かず、自然な余韻で文章を閉じます。
絵文字や装飾としての文末コロン（：）は使いません。紹介記事・宣伝文で書き手が気持ちや勢いを表すために使った絵文字は残します（「紹介記事・宣伝文（promo）」）。
小説の本文や、書き手がダッシュを文体として使っているエッセイでは、言いさしや間、言い換えを表すダッシュを一律に外しません。補足や言い換えを毎回同じ形でダッシュで挟み、その数が多い場合だけ、SKILL.md「装飾記号の排除と太字の表示」に従って見直します。

## 文書の種類と読者

SKILL.md「Step 1: 文脈と段落の把握」の種類と読者の決め方の細部。種類か読者の推定に迷うとき、informed か general を指定されたとき、「ここに説明が必要です」を書くときに読む。書き手と読み手との関係は 「書き手と読み手（ペルソナ）」。どの種類と読者でも、意味を保つこと（SKILL.md「最優先ルール: 意味の保持」）、足さないこと（SKILL.md「情報の不増補（足さない）」）、見出しと節の数と順を変えないことは同じ。

### 2. 読者の手がかり

- 依頼の宛先（「全社員向け」は general、「チームの開発者に」「レビュアーに」は expert、「上長に」は informed）と、置き場所（社内 Wiki、公開のブログ、顧客向けのお知らせ）。
- 本文が略語を説明なしで使っていることは弱い手がかりにとどめる。書き手の想定を示すだけで、読む人が専門家とは限らない。
- 種類から決める既定の読者は、pr と minutes の expert（レビューする開発者と、会議の出席者）だけ。
- 関係を指定されたときは 「書き手と読み手（ペルソナ）」の2章の目安で段階を決めてよい（推定と書く）。関係を推定しただけのときは、この章の手がかりだけで決める。

### 6. 推定のときに使う調整の範囲

| 調整 | 指定（確かめた答えを含む） | 推定 |
|---|---|---|
| 種類で外す規則と、その種類で普通な書き方を直さないこと | 使う | 使う |
| 用語を残し、説明を足さない（expert） | 使う | 使う |
| 識別子が主語の文を直さない（expert、informed） | 使う | 使う |
| 説明が要る所を返す（informed、general） | 使う | 使う |
| 用語を言い換えるか、原文と資料の説明を添える（informed、general） | 使う（8章の条件のとき） | 使わない。語を残して説明が要る所に出す |
| 文を分ける範囲を広げる（general） | 使う | 使わない |

推定で使う調整は、どれも本文を変えないか、変える箇所を減らす向きにだけ働く。推定が外れても、本文の書き換えは種類と読者を決めないときより増えない。

### 7. 読者の3段階

| 値 | 意味 | 用語の扱い | 文の長さと省略 |
|---|---|---|---|
| expert | 文書の分野の用語と前提を共有している | 用語、略語、識別子を残す。説明を足さず、説明が要る所も返さない | 分野で普通の省略を残す。長い文を分けるのは読み違いを特定できたときだけ |
| informed | 一般の技術や業務の語は分かるが、この分野だけの略語、社内の呼び名、前提の手順は知らない | 一般の技術語と業務語は残す。分野の外で通じにくい語と社内の呼び名は、指定されたときだけ原文と資料の説明で言い換えるか添え、ほかは返す | expert と同じ |
| general | 分野の用語と前提を知らない | 説明のない用語は、指定されたときだけ、原文と資料の説明か同じ範囲を指すふだんの語で言い換えるか添え、ほかは返す | 9章 |

- 技術の文書でないとき、informed は「仕事の文書を読み慣れていて、一般の業務の語は分かる人」と読む。
- 開発者向け（読者が expert か informed で、本文がソフトウェアの話）では、識別子が主語の文（`scheduler` が失敗したジョブを再投入する）を擬人化として直さない。「コードが語る」のような本当の擬人化は直す。general でも識別子は言い換えない。

### 8. 用語の扱い

| 分類 | 例（合成） | expert | informed | general |
|---|---|---|---|---|
| A 原文か資料に説明がある用語 | 「TTL（キャッシュを残す時間）」と原文にある | 残す | 残す | 残す |
| B 説明のない分野の用語と略語 | 冪等、p95、減価償却、発注点 | 残す | 一般の技術語と業務語（API、サーバー、売上原価）は残す。分野だけの語は、資料に定義があり指定されたときだけ言い換えるか添え、ほかは返す | 資料に定義があり指定されたときだけ言い換えるか添え、ほかは返す |
| C 社内の呼び名、内部の略語、プロジェクト名 | 青環境、P1対応、月次締め会 | 残す | 返す（資料に説明があり指定されたときは添える） | 同左 |
| D 直訳の語、AIの造語、意味のぼやけた流行語 | 版、回帰、判断OS、解像度 | SKILL.md「専門用語と名称の扱い」と「内容に合わない大げさな名詞の整理」のとおり（`references/rules.md` の「AI生成文の不自然な語彙・構文カタログ」の2章、5章） | 同左 | 同左 |
| E 識別子、コード、画面の項目名、製品名、法令の用語、数値と単位 | `retry_limit`、「保存」ボタン、PostgreSQL | 残す（識別子が主語の文も残す） | 同左 | 残す。言い換えない。要れば返す |
| F 同じ範囲のふだんの語がある外来語 | アサイン、アジェンダ | 残す | 残す | 指定されたときだけ、同じ範囲のふだんの語に言い換えてよい |

言い換えてよいのは、次のすべてを満たすときだけ。

1. 利用者が informed か general を指定した（確かめた答えを含む）。推定では言い換えない。
2. 言い換えの語が原文か資料の定義から取れる。または、ふだんの語で指す範囲が同じと言える（狭めも広げもしない。分類 F）。モデルが知っている一般の知識で定義を書かない。それは原文にない説明になる。
3. 言い換えが1つに決まる。
4. 「変えたところ」に「用語 → 言い換え（読者: general）」と1行で書く。

言い換えない語は、分類 E のすべて、原文で定義された語、見出しや表の項目名と本文で対応している語、引用の中の語。提供された定義や値と状態の対応を説明に使う決まり（SKILL.md「情報の不増補（足さない）」）は、読者によらず同じに当てる。

### 9. 文の長さと省略

- 種類ごとの長さと省略は、この文書の種類ごとの節の3章に従う。
- general を指定されたときだけ、1文に用件が2つ以上あり、つなぎ言葉で関係を残せる文を分けてよい（SKILL.md「文長と読点の調整」の範囲）。推定の general では分ける範囲を広げない。
- 数値の目安は新しく作らない（平均30〜45字の目安は SKILL.md「文長と読点の調整」）。

### 10. 「ここに説明が必要です」の書き方

- 置き場所は「書き手に確かめたい点」。形は `- ここに説明が必要です: 「TTL」（3段落目。原文と資料に説明がない）`。本文には入れない。
- 3点まで。確かめたい点の3点とは別に数える。多ければ、見出し、最初の段落、何度も出る語の順に選び、「ほかに N か所」と添える。
- 語ごとに説明の文案を書かない。説明は書き手が書く（SKILL.md「3. 出力フォーマット」の「書き手に確かめたい点」）。
- expert には出さない。読者を決めないときも出さない。本文だけの指定でも出さない。
- 社外の読み手（関係を指定されたとき）の社内の呼び名には、「説明を足すか、出さないかは書き手が決める」と添えてよい。段階が expert なら出さないのは同じ。
- 確かめたい点は、原文そのものの意味が決まらない所。説明が要る所は、書き手には分かっているが読者には足りない所。同じ語を両方に書かない。新規作成でも、資料に説明がなければ足さずに返す。

## 書き手と読み手（ペルソナ）

SKILL.md「Step 1: 文脈と段落の把握」の、書き手の立場と読み手との関係の細部。どの値でも、意味（数値、否定、条件、確度、誰が何をしたか）を保つこと、原文にない内容（担当者、説明、主張、気持ち、挨拶、お詫び）を足さないこと、構成を変えないことは同じ。例はすべて合成。

   - 書き手の立場と、読み手との関係（上司、取引先など）は、依頼で言われたときだけ使います。言われずに推定しただけなら、本文も知らせも変えず、敬語の揺れや度合いについて、知らせも直す案の申し出も書きません。推定した読み手や関係を、変えなかった理由として書くこと（「社外あての文書なので、丁寧な言い方を残しました」）もしません。言われたら、直す前にこの節を読み、その範囲で本文を直します。上司と社外の読み手には、読み手への依頼と読み手の行為を尊敬語（ご確認ください）に、社外の読み手に向かう書き手の行為を謙譲語（ご連絡いたします）に上げます。形は7章に従い（同じ動詞に「お・ご」を付けた形か、その関係で人がふつう書く言い回し。頼む中身は変えない）、二重敬語と、原文にない「させていただく」は作りません。書き手が自分でした行為で、主語がなくほかの人の行為と読み違えうる所は、原文にある書き手の一人称を主語に補います（チームや会社の決定とも読める文、手順の操作、決まった事柄の文には補わず、3か所まで）。担当者、説明、挨拶、お詫びは足さず、一人称と謙遜は残します。読み手に合わせて語の難しさを上げ下げしたり語句を削ったりせず、人の名前と敬称も変えません。敬語を下げるのは利用者が頼んだときだけで、essay と promo ではペルソナで本文を変えません。ペルソナから出す知らせは、知りえない事情、立場に合わない断定、関係に合わない言い方（一人称、宛先の食い違い、常体）の3つだけで、本文は書き換えず、9章の形で「書き手に確かめたい点」に書きます。ペルソナや敬語について、問題がなかったこと、変えなかったこと、変えなかった理由は、返答の冒頭のまとめ、「変えたところ」（「なし」の後ろの括弧を含む）、確認の記録を含め、返答のどこにも書きません。主語を補わなかった所と、敬語を上げなかった所（同じ動詞の形がない依頼、引用や画面の文言、自分の側の作業）の理由、検査の候補への答えの中で読み手や関係を理由に残した所も、同じく書きません。

### 2. 3つの値と区分

- 書き手: 立場（依頼の言い方のまま）と発信の立場（個人／チームの代表／組織の窓口）。役割（何の担当か）を言われなければ作らない。
- 知っている範囲の目安: 個人なら自分の作業と見聞き（自分の受け持ちの仕事の相手（委託先、取引先、リース会社など）から伝えられた作業の予定と、自分の課・チームの受け持ちの仕事の日程と費用の出どころを含む。部や会社が決めた目標・人数・方針・予算の変更と、書き手が出ていないと原文か依頼に書いてある会議で決まったことは含まない。出たかどうか書いていない会議は、出ていないと決めない）。チームの代表（リーダー、課長、部長）なら、自分が率いるチームや部の作業・決定・目標・数値と、自分が出る会議（部長なら部長会）で決まったこと。役職の名前に部やチームの名前があれば（「経理部の課長」）、その部の決定と目標は知りうる。組織の窓口なら、組織が決めて公表したこと。
- 経路の例: 「〜から聞きました」「朝会で説明がありました」「〜の会議に出席しました」「社内報によると」「〜と案内がありました」「〜と聞いています」「〜とのことです」「議事録を見ると」。どれかが原文か依頼にあれば、知りえない事情として扱わない。
- 読み手: 相手（自由な言葉）、関係（下の7区分）、段階（expert、informed、general。「文書の種類と読者」の7章）。
- 場面: 種類の値（この文書の「種類の一覧」）か「決めていない」。

| 関係 | 例 | 段階の目安 |
|---|---|---|
| 上司・目上 | 上司、部長、研究室の先生 | informed |
| 同じチーム | 同僚、レビュアー | expert |
| 部下・後輩 | 新人、引き継ぐ人 | informed |
| 他部署 | 経理、ほかのチーム | informed |
| 社内の不特定 | 全社員、部の全員 | 全社員は general、部の全員は informed |
| 社外の特定の相手 | 顧客、取引先の担当者 | 相手の言葉から（お客さまは general、取引先の担当者は informed） |
| 社外の不特定 | お客さま全体、公開の記事の読者 | general。技術記事と論文は決めない |

- 段階の目安は関係を言われたときだけ使い、「informed（推定。関係から）」と書く。段階を言われたら、そちらが先。

### 4. 推定のときの範囲

| 調整 | 指定（問いへの答えを含む） | 推定 |
|---|---|---|
| 敬語を上げる、揺れをそろえる（7章） | 関係を言われたとき | しない（知らせもしない） |
| 書き手の主語を補う（5章） | 書き手を言われたとき | しない |
| 社内の呼び名に、同じ文書の中の説明を写す（6章） | 段階を言われ、informed か general のとき | しない |
| 合わない言い方を知らせる（6章） | 関係を言われたとき | しない |
| 知りえない事情を知らせる | 書き手を言われたとき | しない |
| 立場に合わない断定を知らせる | 書き手と関係の両方を言われたとき | しない |
| 段階を関係から決める | する（推定と書く） | しない（「文書の種類と読者」の2章の手がかりだけ） |
| 一人称と謙遜を残す | 残す | 残す |
| 確認の記録の1行 | 書く | 書く |

- 3つとも決めないときは、ペルソナのない直し方とまったく同じになる。

### 5. 誰がの扱い

- 書き手の主語を補う: 書き手を言われたとき、次の3つすべてに当たる文だけ、原文にある書き手の一人称（私、僕、弊社など。原文の語のまま）を主語に補う。
  1. その行為そのものを書き手がしたと、原文（同じ行為を書き手の一人称で書いた文がある。同じ出来事の別の行為を書き手がしたことでは足りない）か依頼（「当番の私が戻しました」）から分かる。
  2. 文に主語がなく、すぐ前の文か同じ箇条（同じ文の中の句を含む）に、別の人、チーム、システムが主語の文や句があり、その行為と読み違えうる。
  3. 原文に書き手の一人称がある（ないときは補わない。一人称を新しく持ち込まない）。
- 補わない文: チームや会社がしたとも読める文（「移行することにしました」「案を考えています」で、誰が決めたか書いていない）、手順書の読み手の操作、決まった事柄を伝える文と、5章の断定に当たる文。役割の名前（当番のエンジニア、リーダー）や人の名前を、主語として作らない。補うのは文書全体で3か所まで。補った所は「変えたところ」に「主語を補った（依頼の書き手。原文の『私が〜』と同じ行為）」の形で1行にまとめる。
- 知りえない事情: 書き手の知っている範囲（2章）の外のこと（組織やほかの部・チームの決定、数値、内部の事情）を、経路も伝聞の語もなく言い切った文。本文は変えず（消さない、伝聞にしない）知らせる。経路が原文か依頼にあれば知らせない。出どころを本文に書くかも問わない（書き手が決める）。知らせる前に、書き手の役職とその文の部・チームを照らす（総務部の部長が総務部の予算を書くのは知りうる）。
- 一人称（僕、私たち、弊社）と謙遜（「私の確認不足で」「初めてなので」「私の方で」の「の方で」）は残す。大げさな語だけは今の規則で直す。一人称が関係に合わないと見えるとき（お客さま宛てのメールの「僕」）は、関係を言われたときだけ合わない言い方として知らせる。
- 立場に合わない断定: 決めるのが読み手（上司、決裁者、取引先）の事柄を、書き手が決めた形で言い切った文だけ知らせる（部長に判断を求める文書の「来期から、週次の定例を隔週にします。」）。書き手が決められる立場の文書（リーダーがチームに出す提案や連絡）では、「提案書」と言われても知らせない。案と分かる文（「〜を提案します」「〜したいと考えています」「案1:」）と、書き手の意見や見通しは知らせない。誰が決めたかを書いていない「〜ことにしました」「〜ことになりました」は書き手が決めた形に当たらず、組織の窓口が組織として決めた条件や予定を読み手に知らせる文も、知らせない。

### 6. 誰にの扱い

- 用語と社内の呼び名に説明が要るかは、段階だけで決める（「文書の種類と読者」の8章、10章）。関係が社外でも、段階が expert なら返さない。依頼で言われた段階が informed か general で（関係から決めた段階は含まない）、同じ文書の中にその呼び名の説明があるとき（後の段落に「検証用の『砂場』」とある）は、初めて出る所にその説明を写してよい。文書の中にない説明は作らず、呼び名や番号を消さず、「ここに説明が必要です」で返す。
- 合わない言い方として知らせるのは、関係を言われたときの次の3つだけ: 一人称が関係に合わない、原文の宛先が指定の読み手と違う、常体の文書を上司や社外に出す（常体と敬体は変えない）。7章で上げる所と、書き手の自分の側の行為が丁寧語であることは知らせない。
- 変えないもの: 7章のほかの敬語、常体と敬体、一人称、人の名前と敬称（書き手が自分を「さん」付けで書いていても）、宛名・署名・挨拶・クッション言葉（7章の結びの定型を除く）、見出し・節・箇条書きの数と順、主張と言い切りの強さ、数値と担当者。挨拶、お詫び、感謝、説明、読み手を示す見出しや冒頭の文を、読み手に合わせて足さない。読み手に合わせて語の難しさを上げ下げしたり、読み手が分かっているからと語句を削ったりしない。SKILL.md「専門用語と名称の扱い」の直し（不自然な直訳や開いた語を分野の用語にする）は、読み手によらず同じに当てる。
- `references/rules.md` の「文書の立場と文末」の「相手との関係…が分かる依頼では…語調を整えます」は、関係を言われたときは7章の範囲で働く。「誰が、誰に、何のために…」は文末の種類を選ぶ基準。同じ節の「用途や読み手を、短い見出しや冒頭の説明で示します」は利用者が求めたときだけ。

### 7. 敬語の度合いの合わせ方

- 述語を働きで分ける。読み手への依頼（〜してください）、読み手の行為、書き手の読み手に向かう行為（送る、連絡する、報告する、相談する、説明する、案内する、返信する、届ける、伝える）、書き手の自分の側の行為（作業する、直す、止める、確かめる、進める、申請する）。ほかの働きの形を根拠にしない。

| 関係 | 依頼、読み手の行為 | 読み手に向かう書き手の行為 | 書き手の自分の側の行為 |
|---|---|---|---|
| 上司・目上 | 尊敬語に上げる | 謙譲語に上げてよい（上げなくてよい） | 変えない |
| 社外の特定の相手、社外の不特定（敬体の文書） | 尊敬語に上げる | 謙譲語に上げる | 丁寧語のまま。丁寧語と謙譲語（〜いたします、〜てまいります）が原文で混ざるときだけ、謙譲語にそろえる（3か所まで） |
| ほかの4区分 | 変えない | 変えない | 変えない |

- 形: 同じ動詞の合う形が原文にあれば写す。なければ、その関係で人がふつう書く言い回しにする。同じ動詞に「お・ご」を付けた形（ご確認ください、お試しください、ご連絡いたします、お送りします）が自然なら、それを使う。決まった形のある動詞（来てください → お越しください）と、関係に合わないくだけた言い方（変更があれば言ってください → 変更があればお知らせください）は、意味と頼みの強さを保って、その形や言い回しにする。同じ動詞の形がないもの（送り直してください）も、人がふつう書く言い回しがあれば言い換えてよい。「〜し直してください」は決まって「再度お〜ください」にせず、その動詞で人がふつう書く形にする（送り直してください → 再度お送りください、見積もりを出し直してください → 改めてお見積もりください）。頼む中身が変わる言い換えはしない（説明や手順を頼む「教えてください」を「お知らせください」にしない）。「教えてください」は「お教えください」にせず、名前や日程のような事柄を尋ねるなら「お知らせください」、説明や手順を頼むなら「ご教示ください」か「教えていただけますか」にする。期限、選択肢、頼みの数と相手、条件は変えない。読み手の行為でも、条件の節（「口座を変える場合は」「登録したら」）と、依頼の文の中の連用（「画面を開き、」）は上げない（依頼の述語で敬意は足りる）。読み手の行為を説明する文（〜で入ります、〜で取り消せます）を上げるときは「〜いただけます」にし、「お〜になります」にしない。
- 社外の特定の相手（敬体の文書）には、表の述語のほかに、読み手に向けた言い回しも、その関係で人がふつう書く形にする。書き手の考えや気持ちを述べる「〜ています」は「〜ております」（考えております、承知しております）、「申し訳ありません」は「申し訳ございません」、「申し訳ないのですが」は「申し訳ございませんが」、読み手にしてもらうことを受ける「〜と助かります」は「〜いただけますと幸いです」、読み手に選んでもらう問い（どちらがよいか）は「どちらがよろしいか」にし、文を「〜ていて、」でつなぐ所は「〜ており、」にする。作業の文（切りました、行いました）は表のとおり丁寧語のままにする。意味、頼みの強さ、誰がするかを変えず、1つの述語に敬語を重ねない。
- 社外の特定の相手（敬体の文書）へのお詫びと、今後の心がけや約束を述べる文は、子どもっぽく聞こえる言い方を、取引先に人がふつう書く言い回しにする。「もっと」は「これまで以上に」（あとが「早めに」のような比べる語なら「これまでより」）、「同じこと」は「同様のこと」、「気をつけます」は「努めます」にし、「〜して、」でつなぐ所は「〜し、」にする。今後も続ける心がけは、表の自分の側の行為の例外として「〜てまいります」で結んでよい（今後はもっと念入りに見直して、同じ手違いを防ぎます → 今後はこれまで以上に念入りに見直し、同様の手違いを防いでまいります）。これは敬語の度合いの直しで、6章の語の難しさの上げ下げには当たらない。お詫びや約束を足さず、中身と誰がするかは変えず、作業の文は上のとおり丁寧語のままにする。
- 作らない形: 二重敬語（おっしゃられる、ご覧になられる、お伺いいたします）、読み手の行為への謙譲語（ご確認してください、ご記入してください）、書き手の行為への尊敬語、原文にない「させていただく」、原文の依頼より重い組み立てへの差し替え（「〜していただけますでしょうか」「〜くださいますようお願い申し上げます」にする）、「どうぞ」「恐れ入りますが」などの言葉の追加、1つの述語に敬語を重ねる形。
- 結びの定型: 上司と社外では「よろしくお願いします」を「よろしくお願いいたします」にしてよい。挨拶とお詫びは足さない。
- 下げる: 同じチーム、部下・後輩の読み手で、利用者が下げることを頼んだとき（「チーム向けにくだけて」など）だけ。頼まれなければ、原文の尊敬語と謙譲語を残す。
- 数えないもの: 「られる」の形、引用や転記、別の読み手に向けた文、名詞（お知らせ、ご案内）、常体の文書（常体のまま。敬語を問わない）。
- 上げた所は「変えたところ」に1行でまとめる（「確認してください → ご確認ください ほか2か所（読み手: 社外の特定の相手）」）。

| 原文 | 関係（指定） | 扱い |
|---|---|---|
| 見積書をお送りします。内容を確認してください。疑問点は窓口の田村まで問い合わせてください。 | 社外の特定の相手 | 「ご確認ください」「お問い合わせください」 |
| 同じ原文 | 同じチーム | 変えない。知らせない |
| 議事録を確認してください。次の会議で説明します。 | 上司・目上 | 「ご確認ください」。「説明します」は「ご説明します」にしてよいが、しなくてよい |
| 不具合を直しました。明日、結果を連絡します。 | 社外の特定の相手 | 「直しました」は残す。「ご連絡いたします」 |
| 端末を登録し直してください。 | 社外の不特定 | 同じ動詞の形はないが、人がふつう書く言い回しがあれば言い換えてよい（「端末を再度ご登録ください」）。知らせない |
| 資料をご確認ください。 | 同じチーム（頼まれていない） | 下げない |

### 8. 場面ごとの注意

- essay と promo: 敬語を上げず、主語を補わず、ペルソナの知らせも出さない（体験と気持ち、勢いは書き手のもの。promo で返すのは根拠のない誇張だけ）。
- incident: 社外の読み手でも、原因の確度と時系列を変えず、お詫びを足さない。書き手の作業の文（止めました、取り消しました）は丁寧語のまま。段階が informed か general の読み手には、社内の呼び名、管理番号、ホスト名を返す。
- proposal: 5章の断定を知らせる。結論を前に出さない。
- minutes: 常体のまま。記録係が出席していない打ち合わせの決定を知っている体の文を知らせる（書き手を言われたとき）。
- manual: 手順の文（〜します）と「〜してください」の連続を残す。部下・後輩でも下げない。手順を足さない。
- 種類を決めない文書（週報、お知らせ、メール）でも、書き手と関係が決まれば同じように働く。

### 9. 知らせ方と示し方

- 置き場所は「書き手に確かめたい点」。本文に書かない。書き手か関係を言われたときだけ出す。ペルソナから出す知らせは次の3つの形だけ。
  - `- 書き手の立場で知りうるか確かめたい: 「…」（3段落目。書き手（新人）がこれを知った経路が原文にない）`
  - `- 立場に合うか確かめたい: 「…」（4段落目。部長に判断を求める文書で、決まったこととして書いている）`
  - `- 読み手との関係に合うか確かめたい: 一人称が「僕」です（1段落目。取引先の方に送る文書です）`
- 数は別に2点まで（確かめたい点の3点とも、「ここに説明が必要です」の3点とも分け合わない）。知りえない事情、断定、合わない言い方の順。多ければ「ほかに N か所」と添える。知らせは箇所と理由だけにし、理由には原文と依頼から分かることだけを書き、原文にない事情を決めつけない。書き足す文や直し方の文案（「〜と書き添える」「〜のように直す」）を書かない。
- 確認の記録の1行: `- 書き手・読み手・場面: 書き手: 新人エンジニア（指定）／読み手: 上司、上司・目上（指定）、informed（推定。関係から）／場面: 決めていない（週報）`。読み手は相手、関係、段階の順。依頼で言われた値は（指定）、言われず推定した値は（推定）。依頼に種類の語（議事録、提案書、PR）があれば場面は指定。決めない値は「決めていない」。
- 上げた所、そろえた所、主語を補った所は「変えたところ」に1行ずつまとめ、理由に読み手か書き手を添える（「（読み手: 社外の特定の相手）」「（依頼の書き手）」）。
- ペルソナに照らして変えなかった所、問題がなかったこと（「上司向けの敬語として合っています」「同じチームなので、どちらの言い方でもそのままにしました」「知りえない事情はありません」）は、報告のどの欄にも書かない。補わなかった所と上げなかった所の理由（「『出し直してください』は形がないのでそのままにしました」「画面の文言なので変えていません」「課の決定なので主語を足していません」）と、検査の候補への答えで読み手を理由に挙げた文（「部長への依頼なので残しました」）も同じ。
